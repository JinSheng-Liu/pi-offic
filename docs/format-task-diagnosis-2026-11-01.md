# 最新格式任务失败诊断与修复

任务：`483e28cb-b52d-4d14-9e4d-3f691da5ba2e`。

## 结论

本次失败发生于已生成格式操作之后，不是换提示词能解决的问题。原始报错为 `Invalid string length`，在修复并重放后又定位了复杂 DOCX 兼容性问题。没有关闭内容保护检查，没有覆盖用户原始文件或提交用户文档的新版本。

## 根因和修改

1. `server/document/package.mjs` 的 canonical 递归把子树 JSON 字符串重新放入 JSON，导致逐层转义膨胀。18 层最小案例的旧结果长度达 6,291,735 字符。改为逐子树 SHA-256 指纹，元素指纹固定为 64 字符，仍检测内容变化。
2. docx4j 格式保存将部分图片、形状和超链接布尔值从 0/1 写成 false/true，并移除 VML gfxdata 的 Base64 空白。原保护比较误判为结构损坏。只对实测涉及的指定命名空间/属性做等价规范化；真实布尔值变化、图形数据变化和未知属性仍受保护。
3. 局部格式代码仅按正文直属段落定位，而 docx4j 的 Body.paragraphs 包含表格和内容控件。真实文档 SDK 遍历为 1,173 段。改为容器遍历、遇段落即停止，不深入段落内图形文本框。块级 AlternateContent 仍明确拒绝局部定位，避免猜测分支。
4. 局部格式原先拒绝带 Word rsid 属性的 run；允许已知元数据后，测试发现 SDK 拆分 run 可能不复制该属性。按原字符范围恢复元数据，再进行逐字符保护校验；若合并跨越不同元数据则拒绝。
